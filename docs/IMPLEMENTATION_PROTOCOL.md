# Протокол реализации UI Editor

Обновлено: 2026-09-06 15:24 UTC.

Протокол определяет порядок изменения проекта. Архитектурные сущности, связи
и инварианты задаёт `Architecture.md`; фактическое состояние и открытые работы
фиксирует `resume.md`; команды пользователя находятся в `README.md`.
Подробности подготовки и выполнения сборок фиксирует `BUILD_AND_RUNTIME.md`.

Каноническая документация находится непосредственно в каталоге `docs`.
Git-коммиты и, при их использовании, Pull Request являются журналом изменений:
завершённые планы, фазы и история отдельных исправлений в действующую документацию
не переносятся.

## Репозитории и условия доступа

Основной репозиторий проекта: https://github.com/y26084670-blip/web-gui
Основная ветка: main
Видимость: private

Чтение:
- учётная запись GitHub.

Изменение:
- рабочие изменения вносятся непосредственно в `main`;
- отдельные ветки и Pull Request используются только по отдельному указанию;
- перед публикацией выполняются предусмотренные для изменения проверки.

## Обновление Markdown-документов

Каждый создаваемый или содержательно изменяемый Markdown-документ должен сразу
после заголовка первого уровня содержать строку:

    Обновлено: YYYY-MM-DD HH:MM UTC.

Дата и время обновляются только вместе с содержательным изменением документа.

Специализация документов сохраняется:

- `README.md` — назначение, окружение и пользовательские команды;
- `BUILD_AND_RUNTIME.md` — режимы сборки, запуска и развёртывания;
- `Architecture.md` — действующая архитектура и технические контракты;
- настоящий протокол — порядок внесения изменений;
- `resume.md` — краткое текущее состояние, открытые работы и очередь ближайших работ.

Одинаковое техническое требование полностью описывается в одном документе.
Остальные документы при необходимости дают ссылку или указывают только статус,
не повторяя условие и реализацию.

## Выбор следующей работы

Если `resume.md` содержит раздел с заголовком «Приоритетные изменения», его
список является актуальной очередью ближайших работ и основным руководством при
выборе следующей задачи.

Выбор пункта определяет следующую задачу, но не заменяет отдельную команду
пользователя на редактирование файлов.

При отсутствии отдельного указания пользователя выбирается первый незавершённый
и незаблокированный пункт списка.

Очередность допускается изменять для учёта зависимостей, совместного изменения
связанных компонентов, объединения проверок, снижения риска или исключения
повторной работы. Причина изменения очередности сообщается до начала реализации.
Перестановка пунктов не должна неявно менять их содержание или согласованный
объём.

Прямое указание пользователя имеет приоритет над списком. Если оно изменяет
дальнейшую очередь, `resume.md` актуализируется в том же цикле работ.

Каждый пункт формулируется как конкретное действие и содержит ожидаемый результат,
необходимые ограничения или зависимости и проверяемый критерий завершения.

После завершения работы выполненный пункт удаляется, а оставшиеся пункты
пересматриваются и при необходимости переупорядочиваются. История выполненных
пунктов в `resume.md` не сохраняется.

Пункт не дублируется одновременно в очереди и общем списке открытых работ. При
повышении приоритета он переносится в очередь, а при откладывании — обратно в
общий список.

Отсутствие раздела с заголовком «Приоритетные изменения» означает, что заранее
определённой очереди ближайших работ нет.

## 1. Подготовка изменения

До редактирования необходимо:

1. определить затрагиваемые компоненты и владельцев ответственности;
2. перечислить точный состав изменяемых, создаваемых и удаляемых файлов;
3. описать назначение, зависимости, риски и возможные регрессии;
4. проверить согласованность с `Architecture.md`;
5. определить автоматические и ручные проверки;
6. получить подтверждение пользователя, если изменение ещё не было явно
   поручено.

Изменение нескольких компонентов допускается одним циклом, когда разделение
оставляет проект в промежуточно несогласованном состоянии. Несвязанные
изменения оформляются отдельно.

## 2. Ограничения исходных данных

Для каждого нового или изменяемого элемента исходных данных разработчик обязан:

1. получить и явно зафиксировать пользовательские требования к допустимым
   значениям;
2. задать ограничения отдельного значения в `property` или `property.items`,
   при необходимости реализовав общий валидатор и его регистрацию;
3. выявить ограничения, зависящие от режима, сочетания полей, математической
   или физической модели, и реализовать их в валидаторе соответствующей
   вкладки из `modelRegistry`;
4. определить источник требования, условие применимости, затрагиваемые поля,
   уровень диагностики и проверки.

Полный набор ограничений не считается автоматически выводимым из типа поля,
формата файла или описания модели. И задание пользовательских ограничений, и
программирование модельных ограничений требуют прямого участия разработчика.

Точное предметное условие хранится в `Architecture.md`; протокол определяет
только обязательный порядок его выявления и реализации.

## 3. Архитектурные изменения

Новые сущности, интерфейсы, атрибуты схемы, каналы данных и инварианты сначала
фиксируются в `Architecture.md`, после чего реализуются в коде.

Если действующий архитектурный контракт ошибочен или препятствует обоснованному
изменению, необходимо:

1. показать противоречие и его последствия;
2. предложить корректировку контракта;
3. согласовать её с пользователем;
4. изменить документацию и реализацию в объявленном объёме.

Локальные исключения, скрывающие нарушение архитектуры, запрещены.

## 4. Реализация

- Изменяется владелец соответствующей ответственности, а не случайный
  потребитель результата.
- Расширение выполняется через действующие registry и descriptor-контракты,
  если архитектурой не согласовано иное.
- Не создаются вторые изменяемые копии BaseModel и дополнительные каналы
  синхронизации для частного случая.
- Косметические и сопутствующие исправления включаются только в заранее
  объявленный объём.
- Несвязанный обнаруженный дефект фиксируется как отдельная работа.

## 5. Проверка

Состав проверок выбирается по конкретному риску и ожидаемой пользе.
Создание тестов и полный запуск `npm test` не являются обязательными для
каждой правки, сборки или публикации. Существующий набор остаётся доступным
для выборочного использования; его количество не является показателем
полноты или эффективности проверки.

Для изменения кода выполняются production-сборка и доступная проверка
изменённого пользовательского сценария. Связанные вкладки и каналы данных
проверяются в объёме возможного влияния. Для UI и File System Access API
учитываются особенности реального браузера.

Тестирование предпочтительно там, где изменение затрагивает расчёты,
сохранность данных, взаимодействие компонентов или трудно заметные регрессии.
Исполнитель выбирает подходящий существующий тест, временную проверку вне
исходного кода либо ручной сценарий. Новый постоянный тест имеет смысл, когда
ожидаемая повторная польза оправдывает его сопровождение. В отчёте указываются
проверенный риск, результат и существенные ограничения; число успешных
проверок само по себе не заменяет это объяснение.

Документационное изменение проверяется поиском устаревших ссылок, терминов и
дублирующихся нормативных формулировок. Если проверку нельзя выполнить в
текущем окружении, это явно указывается в отчёте.

## 6. Завершение и отчёт

Изменение публикуется коммитом непосредственно в `main`. Отдельная ветка и
Pull Request используются только по отдельному указанию пользователя. В отчёте
указываются:

1. изменённые, созданные и удалённые файлы;
2. суть изменения и затронутые контракты;
3. выполненные автоматические и ручные проверки;
4. ограничения проверки и оставшиеся работы;
5. итоговый commit в `main`; при использовании отдельной ветки — её имя и Pull Request.

После завершения подтверждённого объёма новые несвязанные изменения без
отдельного согласования не добавляются.

## Локальный помощник

Связанные изменения помощника выполняются через отдельную ветку и draft PR
с перекрёстной ссылкой на PR clark.agent. Обновление main требует отдельной команды.

Межпроектный контракт принадлежит clark.agent; GUI фиксирует клиентские обязанности
и настройку в AGENT_INTEGRATION.md. Изменение протокола сопровождается проверкой
реального клиента с сервером и SQLite, не только mock-тестами.

Не относящиеся к агенту изменения модели, валидаторов, сохранения и LAN-публикации
не включаются в этот инкремент. Работоспособность редактора без агента обязательна.
