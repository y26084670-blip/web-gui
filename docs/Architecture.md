# UI Editor — Архитектурный контракт проекта

Обновлено: 2026-08-29 17:37 UTC.

## Назначение
Документ является единственным архитектурным контрактом проекта и описывает
действующую архитектуру и её принципы.

Документ описывает архитектуру, а не журнал изменений. Порядок внесения
изменений определён в `IMPLEMENTATION_PROTOCOL.md`, фактическое состояние и
открытые работы — в `resume.md`.

Архитектурная концепция изменяется только после предварительной фиксации в
канонических документах.

Запрещается:

- нарушать границы ответственности компонентов ради локального упрощения;
- вводить архитектурные соглашения только в коде.

Масштабные рефакторинги, согласованные изменения нескольких компонентов,
косметические и сопутствующие улучшения допускаются, если заранее определены
их цель, полный объём, зависимости, риски и способ проверки.

---

# Основные архитектурные принципы
- Design by Contract: `createSchema` — контракт; конфигурация в целом не валидируется, 
  проверяются только контрактные условия и пользовательские данные.
- Registry Architecture: formatter / editor / constraint / model / view —
  реестры; расширение без изменения диспетчеров.
- Три инструмента на значение: formatter, editor, validator — выбираются по
  `property.type`, независимы друг от друга, расширяются регистрацией.
- Единственная точка определения свойства — `resolveProperty()`.
- Трёхуровневая модель данных: StorageModel, BaseModel, Tabulator ViewModel.
- Разделение валидации: constraintValidator (ограничения ячейки),
  modelValidator (прикладная согласованность).
- Независимость типа данных от способа отображения.
- Единственный владелец у каждого производного знания: форма массива,
  подпись строки, конфигурация ячейки-значения, инвариантные опции таблицы.

# Архитектурное описание

## Компоненты
Schema (createSchema, tabRegistry), StorageModel, BaseModel, modelSerializer,
modelCompute, arrayShape, modelConverter, variantChange, arrayViewCodec,
computedView, rowLabel, TableBuilder, tableOptions.

`modelCompute` — единственный владелец общего графа
`compute`/`computeStored`, определения участия свойства в StorageModel,
нормализации BaseModel и формирования transient-патчей вычисленных значений.

Инструменты обработки значения: universalFormatter / formatterRegistry,
universalEditor / editorRegistry / editorFactory, constraintValidator /
реестр ограничений.

Представления: ViewRegistry, ViewAdapter, View (TableView), DetailRegion и
основная View-проекция свойства вкладки.

Прикладная проверка: modelValidator, modelRegistry.

Сервисы состояния: modelService, diagnosticService, selectionService,
selectionContextService, clipboardService, dataService.

Базовые характеристики обслуживают `defaultLibraryService` и отдельный
`materialTabRegistry`. Чтение, копирование, импорт, редактирование и удаление в
локальной библиотеке выбранного задания выполняет
`taskMaterialLibraryService`; отдельную ревизию файлов публикует
`materialLibraryRevisionService`. Эти операции не изменяют BaseModel задания
и не участвуют в общей истории Undo/Redo.

`selectionService` хранит выбранное задание, его путь и версию загруженных
данных. `selectionContextService` хранит активный экземпляр таблицы и ревизию
его выделения для операций панели; он не владеет выбранным заданием и не
дублирует состояние `selectionService`.

`fileSystemAccessSupport` является единственным владельцем проверки клиентского
окружения для операций с локальными файлами. Перед открытием системного диалога
UI проверяет `window.isSecureContext` и наличие требуемого метода File System
Access API. Официально поддерживаются актуальные настольные Google Chrome и
Microsoft Edge. Отдельный Chromium SDK на клиенте не требуется.

Корневой каталог проектов выбирается с `mode: "readwrite"`: одно разрешение
покрывает чтение исходных данных, обычное сохранение и запись локальных
характеристик. Отдельно выбираемые legacy-каталоги ВТСП открываются только для
чтения; `XAP.lib` читается через уже выбранный каталог задания.

Отказ пользователя в системном диалоге представлен только `AbortError` и
обрабатывается без сообщения. Небезопасный контекст, отсутствие API, отказ в
разрешении и прочие ошибки открытия системного файлового диалога показываются
пользователю в модальном окне; их запрещено оставлять только в консоли или
подавлять.

Допустимое направление зависимостей: UI и View → адаптеры и реестры → чистые
форматтеры, валидаторы и модельные модули. Форматтеры, валидаторы и schema не
зависят от TableView или UI-компонентов.

## Слои данных
• StorageModel — представление на диске: CLUSTER — один JSON-объект,
  RECORDS — JSON Lines; значения ARRAY хранятся плоско. Плоское значение
  формально рассматривается как матрица 1×N; отдельная сущность одномерного
  массива не вводится.
• BaseModel — модель в памяти, хранится в modelService по id вкладки;
  значение ARRAY — массив строк, строка — массив значений.
• Tabulator ViewModel — строки и колонки основной таблицы и связанных
  представлений.

Преобразования: modelSerializer (StorageModel ↔ BaseModel), modelConverter (BaseModel ↔
строки Tabulator).

Сопоставление свойств BaseModel с данными хранения выполняется
`modelSerializer` через `property.storageKey`; при отсутствии используется имя
свойства схемы. Простое значение `storageKey` обозначает ключ верхнего уровня.
Точечная запись, например `sym.vi`, обозначает путь по вложенным объектам
StorageModel: точки являются разделителями пути, а не частью имени ключа.
При записи отсутствующие промежуточные объекты создаются. Чтение,
формирование набора объявленных ключей и диагностика используют одинаковое
толкование пути.

Форма хранения ARRAY — базовое число колонок, ориентация `order`,
преобразование между плоским StorageModel и строками BaseModel, канонические
ключи ячеек — описывается единственным модулем `arrayShape`.
`modelSerializer`, `modelConverter`, `dataService` и `TableView`
используют его и не содержат собственных правил формы или ориентации.
Вариантная проекция может показывать другое число строк и колонок, но не
переопределяет `nColumns`, `order` или форму BaseModel.

Вариантный codec ARRAY преобразует только BaseModel-значение в строки
связанного представления и обратно. Он может изменить число и подписи видимых
строк и колонок, но не форму BaseModel и не правила StorageModel ↔ BaseModel.
Codec является чистым: получает значение, BaseModel-запись и дескриптор,
не получает Tabulator, сервис модели или файловые сущности и не изменяет
входные данные.

Действующий контракт codec:

- `dependencies: string[]` — непустой список свойств той же BaseModel-записи;
- `decode({ value, record, property })` возвращает объект с двумерным
  `rows`, непустым массивом `columns` и при необходимости
  `itemLabels`, `itemLabelTitle`, `key`;
- `encode({ rows, record, property, presentation })` возвращает
  BaseModel-значение ARRAY;
- `onDependencyChange({ value, record, property, dependency, oldValue,
  newValue })` при наличии возвращает BaseModel-значение после реакции.

`key` — необязательная идентичность конфигурации представления.
Если codec её не возвращает, инфраструктура формирует идентичность из
`dependencies`. Изменение зависимости публикует внешнюю ревизию даже при
отсутствии `onDependencyChange`; изменение идентичности перестраивает
колонки и строки.
Отсутствующий результат `decode`, не-объект, не-массив `rows` или пустой
не-массив `columns` заменяются соответствующими статическими атрибутами
свойства; исключение codec не маскируется. Семантическая корректность строк
является ответственностью реализации codec.

`modelService` публикует изменение части BaseModel вместе с возрастающей
ревизией и необязательным transient source ID; отсутствие source обозначает
внешнюю публикацию. Слой вкладки применяет внешнюю ревизию к
Tabulator и подавляет обратную публикацию при применении. Обычная правка
проходит по единому пути Tabulator → BaseModel; модельная реакция затем
публикует полученную BaseModel обратно в Tabulator. Таким образом изменения
модели вне таблицы не создают вторую рабочую копию данных.

Реакция `variantCodec.onDependencyChange` запускается для точечной правки,
зафиксированной редактором. После неё общий механизм
`compute`/`computeStored` выполняет граф вычислений до единственной
публикации BaseModel.
Оба механизма используют тот же revision/source-канал и не создают второй
канал синхронизации.

## Вычисляемые свойства BaseModel

Вычисляемое свойство выводится из других свойств той же BaseModel-записи.
Действуют два взаимно исключающих дескриптора:

- `compute: { dependencies, evaluate }` — значение существует в BaseModel и
  ViewModel, но не входит в StorageModel;
- `computeStored: { dependencies, evaluate }` — значение пересчитывается тем
  же способом, остаётся частью StorageModel и записывается в файл.

`dependencies` — непустой массив уникальных имён других свойств той же схемы.
Зависимость может быть скалярной или составной. По умолчанию действует
`scope: "record"`: для CLUSTER весь объект считается одной записью, для
RECORDS каждая запись пересчитывается независимо, а зависимость может ссылаться
на другое вычисляемое свойство.

Для RECORDS допускается `scope: "records"`. Такой descriptor получает
неизменяемый снимок всей коллекции и индекс текущей записи, поэтому может
вычислять значение из физически предшествующих записей. Его зависимости
обязаны быть исходными, а не вычисляемыми свойствами; межвкладочные зависимости
по-прежнему не поддерживаются.

Сигнатура функции:

```js
evaluate({
    values,
    property,
    propertyName,
    recordIndex,
    records,
}) => value
```

`values` содержит копии только объявленных зависимостей в их актуальном
топологическом состоянии. `recordIndex` задаётся для RECORDS, а `records` —
только для `scope: "records"`. Функция синхронна и чиста: не изменяет вход,
не получает Tabulator, `modelService` или файловые сущности и не хранит
состояние. Promise и `undefined` являются нарушением контракта; исключение
не маскируется default или прежним значением. Результат клонируется перед
помещением в модель.

`createSchema` проверяет взаимное исключение `compute`/`computeStored`,
форму дескриптора, существование, уникальность и отсутствие self-зависимостей,
а также циклы общего графа. Граф выполняется один раз в стабильном
топологическом порядке; повторные итерации до сходимости не применяются.
Зависимость `variantCodec` от вычисляемого свойства в действующем контракте
запрещена, поскольку вариантная реакция предшествует общему пересчёту.

Оба вида вычисляемых свойств семантически readonly независимо от явного
`readonly`. `readonly: false` и `const` несовместимы с ними.
Связанное представление вычисляемого ARRAY доступно для просмотра, но
редактирование значений и структурные операции запрещены. Явный `default`
остаётся начальным значением и описанием формы свойства до первого пересчёта,
но не заменяет результат функции.

Пересчёт выполняется:

- после десериализации StorageModel;
- при создании default CLUSTER или новой RECORDS-записи;
- после каждой правки или структурной операции Tabulator, вслед за вариантной
  реакцией;
- при любой публикации части BaseModel через `modelService`;
- повторно перед сериализацией как защитная нормализация.

`modelService.setModelPart(schema, data, { source })` завершает весь пересчёт
до назначения одной revision. В update вместе с нормализованной BaseModel
передаётся transient-список изменённых вычисляемых полей. Для собственной
публикации DataEditor применяет поле точечно, если оно представлено одной
существующей строкой; это не закрывает связанное представление и не заменяет
объект строки. Если значение развёрнуто в переменное число строк
(ARRAY без `nColumns` в CLUSTER), применяется полная BaseModel с безопасным
закрытием прежнего связанного представления. Для внешней публикации также
сохраняется последовательное полное применение BaseModel. Патчи, revision и
source не входят в BaseModel и не сериализуются.

В схеме `elements` вычисляются `yc1…yc4`, `eoCount`, `eoCountAll`,
`isConductive`, `isMagnetic`, `isAnisotropic` и `eoRange`. Поле
`eoRange` использует `scope: "records"`: диапазон глобальных номеров ЭО с
независимыми источниками определяется значением `eoCount` текущей записи и
суммой соответствующих счётчиков всех физически предшествующих записей
`elements`, независимо от `targ`. Вычисляемые поля не входят в JSON.

## Стыковка с расчётным модулем
Проект `clark.gui` является источником истины исключительно для формата файлов
исходных данных `input3XX`: имён каталогов и файлов, состава и имён JSON-ключей,
структуры и вложенности JSON, порядка записей, а также порядка и ориентации
сериализованных данных. Решатель на Julia обязан читать и писать этот формат.

Проект `clark.std.jl` является источником истины для математических алгоритмов,
физических понятий, семантики значений, формул, вычисляемых величин и правил
математической интерпретации исходных данных. Перенесённая в GUI вычислительная
логика должна соответствовать реализации Julia.

Подтверждённый дефект исправляется в проекте, которому принадлежит
соответствующая ответственность. Наличие дефекта не изменяет границы
ответственности и не переносит статус источника истины другому проекту.

Соответствие файлов и вкладок:

| Файл           | Вкладка             | Хранение |
|----------------|---------------------|----------|
| general.txt    | Общие параметры     | CLUSTER  |
| conrab.txt     | Конфигурация модели | RECORDS, ровно 2 записи |
| kvs.txt        | Элементы модели     | RECORDS  |
| tks.txt        | Области наблюдения  | RECORDS  |
| amplitudes.txt | Амплитуды           | RECORDS  |
| moves.txt      | Траектории          | RECORDS  |
| mhj.txt        | Заданные источники  | RECORDS  |

Необязательная проекция `views.graph` схемы RECORDS описывает
линейный график выделенных записей. Каждый режим проекции
ссылается на одно свойство ARRAY/TABLE, задаёт колонку абсциссы,
подписи осей и одну или несколько колонок рядов. Если режимов
несколько, `defaultMode` определяет начальный выбор. Проекция не
создаёт копию BaseModel: она читает текущие ViewModel-строки выделения
и перестраивается после смены выделения или редактирования данных.

Вкладка «Амплитуды» показывает один ряд «время — амплитуда» на
каждую выделенную запись. Вкладка «Траектории» показывает по три
ряда X/Y/Z на запись и переключает источник между смещением и
углами; по умолчанию выбрано смещение. График и `DetailRegion`
располагаются рядом под основной таблицей.

`conrab.txt` содержит ровно две JSON Lines-записи с одинаковым полным набором
полей: первая задаёт рабочие константы Float32, вторая — Float64. Однострочный
файл, пустая запись, лишняя запись или не-объект считаются ошибкой загрузки.
В BaseModel профили сохраняют обычную RECORDS-форму; только представление
транспонирует их в таблицу `Параметр | Float32 | Float64`. Структурные операции
над двумя фиксированными записями запрещены, а редактирование любой профильной
ячейки проходит через обычную историю вкладки.

`mhj.txt`, если существует, содержит ровно одну RECORDS-запись `{ v }`.
Одна строка JSON Lines физически совпадает с одиночным JSON-объектом, который
читает решатель; вторая запись недопустима, поскольку решатель её не прочитает.
Схема файла необязательна. При отсутствии файла и нулевом требуемом числе строк
BaseModel вкладки остаётся `null`, поэтому обычное сохранение файл не создаёт.
Существующий файл автоматически не удаляется.

### Библиотеки характеристик

Каноническая базовая библиотека редактора находится в tracked-каталоге
`data/default` и включается в статические ресурсы сборки через детерминированный
индекс и контрольные суммы SHA-256. Она содержит `xapLibFMM` и `xapLibHTC`,
доступна только для чтения и не требует серверного API или режима администратора.
Индекс запрашивается без использования устаревшей браузерной копии. URL каждого
файла характеристики содержит его SHA-256, поэтому неизменившиеся файлы могут
кэшироваться, а новая версия всегда получает новый URL. В конфигурации Caddy
`/data/default/*` обслуживается только как статический ресурс и при отсутствии
файла возвращает HTTP 404, не подменяясь страницей `index.html`.

Последние две вкладки приложения — «Характеристики ФММ» и «Характеристики
ВТСП». Они зарегистрированы отдельно от `tabRegistry`, поэтому не загружаются
как часть задания, не сохраняются общей командой и не создают Undo/Redo-историю.
Обе вкладки используют RECORDS-таблицу характеристик и `DetailRegion`: ФММ
показывает таблицу H–M из 12 строк, ВТСП — таблицу скалярных параметров.
Выделенные характеристики ФММ одновременно отображаются линейными графиками
M(H), по одному набору данных и элементу легенды на характеристику.
Горизонтальный разделитель регулирует высоту общей нижней области ФММ, а
вертикальный — соотношение ширины таблицы H–M и графика. Оба разделителя
поддерживают перетаскивание указателем и управление клавишами со стрелками.
3D-визуализация в текущий контракт не входит.

Выделенные базовые характеристики копируются побайтово только в
`input3XX/xapLibFMM` или `input3XX/xapLibHTC` выбранного задания. Совпадающий
локальный файл не перезаписывается; отличающийся файл заменяется только после
явного подтверждения пользователя. Браузерный legacy-импорт полностью разбирает
и проверяет `XAP.lib` из корня задания либо выбранный каталог ВТСП до начала
пакетной записи, а
затем создаёт JSON-файлы в той же локальной библиотеке задания. Конфликт всего
пакета определяется до первой записи и требует единого явного подтверждения.
Подтверждение привязано к точному набору путей и SHA-256; изменение файла между
диалогом и повторной проверкой требует нового подтверждения. File System Access
API не предоставляет атомарную транзакцию для нескольких файлов, поэтому ошибка
носителя после начала записи показывается как частичное выполнение с числом
завершённых, ошибочного и оставшихся файлов. Ни копирование, ни импорт не изменяют
базовую библиотеку.

Вкладка ФММ переключается между базовой readonly-библиотекой и локальной
библиотекой задания; перед асинхронной загрузкой нового источника строки старого
источника удаляются. Очистка и заполнение Tabulator выполняются последовательной
очередью: завершившаяся позднее операция старого источника не может перекрыть
новый выбор. Базовые строки всегда readonly. Для локальных строк
непосредственно редактируются название, `hip`, комментарий и 12 пар H–M;
добавление, удаление и перестановка строк H–M запрещены. Изменения накапливаются
в представлении и записываются отдельной командой «Сохранить».

Изменение названия переименовывает JSON-файл. Перед записью проверяются SHA-256
исходной версии и отсутствие другого файла с новым именем; исходный файл
удаляется только после успешной записи нового. Удаление выбранных характеристик
требует подтверждения в модальном окне. Команда «Импортировать» относится к
локальной legacy-библиотеке старого формата и недоступна, если в корне задания
нет `XAP.lib`. Изменения библиотек имеют отдельную реактивную ревизию и не
перезагружают BaseModel задания.

`elements.xapName` является readonly-колонкой. Команда «Выбрать характеристику»
панели вторичной функциональности читает соответствующую локальную библиотеку:
ФММ для `model ∈ {0, 1}` и ВТСП для `model = 2`. Одно выбранное имя без `.txt`
назначается всем выделенным элементам совместимого вида одной публикацией
BaseModel и одним действием Undo/Redo. Смешанный выбор ФММ- и ВТСП-элементов
отклоняется до открытия списка характеристик.

Сведения, которые GUI не выводит самостоятельно и получает из решателя:

- состав и имена ключей каждого файла;
- ориентация развёртки плоских массивов относительно таблиц редактора;
- состав перечислений и соответствие «значение — подпись»;
- правила интерпретации geo в зависимости от geoType;
- перечень производных величин и формулы их вычисления;
- какие величины вычисляет решатель, а какие обязан подготовить редактор.

### Ориентация развёртки плоских массивов

Хранимый плоский ARRAY рассматривается как двумерное значение 1×N.
При отображении он преобразуется в таблицу с числом колонок `nColumns`.
Атрибут дескриптора `order` определяет именно это преобразование, а не вводит
отдельный тип одномерного массива:

- `order: "column"` — значения плоского хранения заполняют колонки таблицы;
- `order: "row"` — последовательные группы по `nColumns` образуют строки;
- при отсутствии `order` используется `"column"`, что сохраняет поведение
  существующих схем.

Поэтому `geo` остаётся плоским значением в StorageModel, формально 1×N, но
для табличного представления его последовательные тройки образуют строки
8×3 или 4×3 и описываются `order: "row"`.

| Поле                                          | Форма                                         | Ориентация                               |
|-----------------------------------------------|-----------------------------------------------|------------------------------------------|
| `impuls` (amplitudes)                         | n×2                                           | column-major                             |
| `angle` (moves)                               | n×4                                           | column-major; колонки: Время, aX, aY, aZ |
| `position` (moves)                            | n×4                                           | column-major; колонки: Время, X0, Y0, Z0 |
| `v` (mhj)                                     | n×3                                           | column-major                             |
| `geo` (kvs, `geoType = 0`)                    | 8×3                                           | row-major                                |
| `geo` (tks, `geoType = 0`)                    | 4×3                                           | row-major                                |
| `geo` (прочие `geoType`)                      | плоский набор параметров                      | —                                        |
| `dr`, `vkan`, `sym.vi`, `sym.r0`, `dp`, `med` | плоский вектор                                | —                                        |
| `services/solver/kvDerived.js::nodeCount`     | `src/core/types.jl` (`Amplitude.n`, `Move.n`) | пересчёт `n` по числу строк              |

Хранимое вычисляемое поле `n` не показывается в основных таблицах, но
остаётся обязательной частью StorageModel и пересчитывается перед записью:

- `Amplitude.n = impuls.length` в BaseModel;
- `Move.n` равно общему числу строк `angle` и `position`;
- для валидной записи `angle.length === position.length === Move.n`;
- при несовпадении длин `Move.n` получает нейтральное значение `0`, а
  запись остаётся ошибочной. GUI не выбирает одну из таблиц источником истины
  и не добавляет или удаляет строки автоматически.

Правило приоритета формата: для строк таблицы, описывающих форму и ориентацию
данных на диске, при расхождении сериализации GUI и чтения или записи Julia
корректным считается формат GUI; исправлению подлежит код ввода-вывода Julia.
Это правило не распространяется на `nodeCount`, математические алгоритмы и
семантику значений: для них источником истины является Julia.
Сопоставляемые участки реализации Julia: `src/base/01_common.jl::fcopy`
(column-major), `src/core/03_kv.jl::unpack` (`reshape(geo,(3,8))`).

### Вариантное представление и смена geo

Каноническая длина валидного хранимого `geo` постоянна и не зависит от
`geoType`: 24 значения для `kvs` и 12 для `tks`. После преобразования
`arrayShape` каноническая форма BaseModel составляет соответственно
матрицу 8×3 или 4×3 с `order: "row"`. Укороченное входное значение не
нормализуется молча; его отдельная диагностика относится к рабочей схеме.

Для `geoType = 0` связанное представление показывает матрицу вершин с
колонками X, Y, Z. Для параметрических вариантов codec разворачивает
BaseModel через `arrayShape`, показывает значащий префикс как фиксированные
именованные строки с одной колонкой и при обратном преобразовании дополняет
хвост буфера нулями. Неизвестный строго типизированный `geoType` использует
сохраняющее матричное представление: значение не переинтерпретируется и не
стирается.

Вариант выбирается по объявленной зависимости `geoType`.
`property.variantCodec` содержит непустой `dependencies`, чистые
`decode` и `encode`, а при необходимости —
`onDependencyChange`. Последняя функция вызывается модельным слоем, а не
View. Для `geo` смена одного известного `geoType` на другой известный
тип обнуляет весь буфер, поскольку одинаковые позиции имеют несовместимую
семантику в разных вариантах. Переход к неизвестному значению использует
сохраняющий fallback и не стирает буфер. Реакция выполняется независимо от
того, открыто ли связанное представление.

Строки `geo` семантически фиксированы, поэтому схема объявляет
`rowsMutable: false`. Панель не показывает структурные команды, а общий
обработчик операций дополнительно запрещает их выполнение.

`unpackKvVertices` и `unpackTkVertices` используются только для получения
производных вершин. Для редактирования параметрических вариантов они
неприменимы: обратного преобразования вершин в исходные параметры нет.

Источник состава и длины значащего префикса:
`src/core/03_kv.jl::unpack`, `src/core/03_tk.jl::unpack`.
Полный сброс является политикой GUI, принятой из-за несовместимой семантики
одинаковых позиций разных вариантов.

### Требования решателя к порядку записей

- Записи `kvs.txt` располагаются группами по возрастанию `targ`: 0, 1, 2, 3.
  Решатель адресует записи срезами `kvs[1:NV1]`, `kvs[NV1+1:NV]`; нарушение
  порядка не диагностируется и даёт неверный расчёт.
- Внутри группы `targ = 0` записи с `model = 2` (ВТСП) предшествуют остальным проводящим.
- Требуемое число строк `mhj.v` равно сумме `eoCount` записей с
  `targ ∈ {1, 2}`. Во время редактирования фактическое число строк
  хранимого `v` может отличаться. При доступной BaseModel `elements`
  проверка модели сообщает об этом как об ERROR с фактическим и требуемым
  числами строк, но не блокирует загрузку, редактирование или сохранение
  и не изменяет `v` автоматически.

Источник: `src/task/01_counters.jl::evalCounters`, `src/vsolver/04_mhj.jl::mhjRecall!`.

### Состав таблицы заданных источников (mhj)

Строки образуются последовательным перебором записей `kvs` с `targ = 1`,
затем `targ = 2`, сплошным потоком без разделения групп. Порядок внешней
записи и вложенных циклов:

    KV (полный массив elements) →
    D12 (kv.dp[1]) → D13 (kv.dp[2]) → D15 (kv.dp[3]) →
    LS (kv.sym.ls) → AS → PS

Границы AS и PS принимают значения `kv.sym.as` и `kv.sym.ps` только для
геометрического типа симметрии (`kya = 0`, `kyp = 0`); в остальных случаях — 1.

Колонки таблицы:

| Колонка                    | Содержание                                                   | Вычисляемая |
|----------------------------|--------------------------------------------------------------|-------------|
| `№ ЭО`                     | сплошной 1-based номер ЭО внутри текущей записи `elements`   | да          |
| `№ ЭО общий`               | номер ЭО с учётом всех физически предшествующих элементов     | да          |
| `KV`                       | 1-based номер записи в полном массиве `elements`             | да          |
| `D12`, `D13`, `D15`       | индексы разбиения вдоль направлений рёбер 1–2, 1–3 и 1–5     | да          |
| `LS`                       | номер образа локальной симметрии                              | да          |
| `AS`                       | номер геометрического азимутального образа                    | да          |
| `PS`                       | номер геометрического периодического образа                   | да          |
| `Mx [кА/м] / Jx [А/кв.мм]` | x-компонента `v`                                             | нет         |
| `My [кА/м] / Jy [А/кв.мм]` | y-компонента `v`                                             | нет         |
| `Mz [кА/м] / Jz [А/кв.мм]` | z-компонента `v`                                             | нет         |

Порядок индексных колонок точно соответствует вложенности циклов
`mhjRecall!`: `KV → D12 → D13 → D15 → LS → AS → PS`; индекс `PS`
изменяется быстрее всего. `№ ЭО` увеличивается в том же порядке и
сбрасывается для каждой записи `elements`. `№ ЭО общий` равен локальному
номеру плюс сумма `eoCount` всех физически предшествующих записей
`elements`, независимо от их `targ`; поэтому в таблице источников возможны
разрывы глобальной нумерации. `LS`, `AS` и `PS` являются номерами
образов, а не общим числом образов.

Смысл величины определяется `targ` записи `kvs` (намагниченность либо плотность
тока); разделения строк по `targ` в таблице нет.

Источник: `src/vsolver/04_mhj.jl::mhjRecall!`, `src/core/03_kv.jl::limits`.

### Вычисляемые колонки ARRAY-представления

ARRAY-свойство может объявить отдельный descriptor представления:

```js
computedView: {
    dependencies: ["elements"],
    columns: [
        { key: "kv", label: "KV" },
        // ...
    ],
    rows({ models, property, rowLimit }) {
        return sourceRows.slice(0, rowLimit);
    },
}
```

`dependencies` содержит уникальные идентификаторы других вкладок.
`rows` — чистая синхронная функция, получающая копии только объявленных частей
BaseModel, статический descriptor свойства и `rowLimit` — фактическое число
строк хранимого ARRAY-представления. Она возвращает не более `rowLimit`
объектов и не обязана материализовать неотображаемый хвост внешней раскладки;
`columns` задаёт уникальный ключ, подпись и необязательное описание каждой
вычисляемой колонки. Значения вычисляемых ячеек являются скалярными данными
ViewModel.

Локальную форму descriptor проверяет `createSchema`; после сборки
`tabRegistry` отдельная контрактная проверка подтверждает существование всех
вкладок-зависимостей. `computedView` не является `compute` или
`computeStored`: он не создаёт свойства BaseModel и не участвует в графе
модельного пересчёта.

`TableView` помещает вычисляемые readonly-колонки перед редактируемыми
колонками значения. Они не получают editor или validator, не входят в строки
BaseModel и не сериализуются. Внутренняя идентичность строки остаётся отдельным
transient-полем и не выводится из вычисляемых значений.

Число редактируемых строк определяет только хранимое ARRAY-значение. Строки
внешнего источника присоединяются позиционно: лишние строки источника не
материализуются, а при их нехватке вычисляемые ячейки остаются пустыми.
Изменение внешней вкладки обновляет только вычисляемые значения; оно не
добавляет, не удаляет, не переставляет и не перепривязывает хранимые строки.

Подпиской на ревизии объявленных внешних вкладок владеет `DataEditor`.
Он передаёт `TableView` актуальный снимок через контекст представления и
обновляет активный `TableView` независимо от его размещения. `TableView`
не импортирует и не подписывает `modelService` непосредственно. Поскольку
вычисляемые значения не хранятся в строках Tabulator, изменение их сигнатуры
явно переформатирует только ячейки readonly-колонок `computedView`; общий
`redraw` не считается достаточным. Для скрытой вкладки переформатирование
откладывается до восстановления видимости.

Схема может объявить основную View-проекцию:

```js
views: {
    main: { property: "v" },
}
```

`views.main.property` ссылается на единственное свойство RECORDS-схемы.
Свойство обязано быть ARRAY с `view: TABLE`. В этом режиме его `TableView`
занимает основную область вкладки непосредственно: внешняя RECORDS-оболочка
не отображается строкой со summary и `DetailRegion` для свойства не создаётся.
Это только проекция View; BaseModel `[{ v }]`, StorageModel, сериализация и
файловый формат не меняются.

Для optional-файла состояния `null` и `[]` дают пустую основную таблицу
независимо от schema-default и не материализуют запись. Первое явное добавление
строки создаёт одну запись `[{ v }]`; удаление последней строки уже созданной
записи оставляет `[{ v: [] }]`. Значение с более чем одной RECORDS-записью
либо записью, где выбранное свойство не является ARRAY, не проецируется молча:
основное представление блокирует изменение, данные сохраняются в BaseModel, а
прикладной валидатор сообщает ERROR.

Поскольку у основной проекции отсутствует родительская ячейка-summary,
ARRAY-level ограничения `minItems`, `maxItems` и `uniqueItems` в этом
режиме пока не поддерживаются и отклоняются `createSchema`. Ограничения
`property.items` продолжают действовать в редактируемых ячейках View.

Для `mhj` функция источника — `mhjRows(elements)`, а `views.main` проецирует
`v` как основную таблицу. Если требуемое число строк положительно, а
единственная запись `mhj` отсутствует, прикладной валидатор создаёт ERROR.
Существующий файл с нулём или более чем одной RECORDS-записью также ошибочен.
Для структурно корректной записи `[{ v }]` при доступной BaseModel `elements`
валидатор сравнивает `v.length` с `mhjRowCount(elements)`. Несовпадение
является ERROR, но не переводит основную проекцию в readonly-состояние, не
мешает сохранению и не добавляет, не удаляет, не переставляет и не
перепривязывает строки. Пользователь самостоятельно согласует `v` с
параметрами элементов и повторно запускает проверку модели.

После каждой ревизии `elements` вычисляемые индексы обновляются автоматически.
Если текущая раскладка короче загруженного `v`, оставшиеся вычисляемые ячейки
остаются пустыми: GUI не создаёт несуществующие итерации решателя. Равенство
числа строк не доказывает смысловую привязку после перестановки элементов;
автоматическое восстановление такой привязки не выполняется.

Правило: математическая и физическая интерпретация данных не восстанавливается
по комментариям и образцам файлов. При отсутствии сведений работа
останавливается и запрашивается уточнение по коду решателя. Формат файлов при
этом определяется проектом GUI и не выводится из реализации Julia.

### Перенесённая математика решателя
Часть алгоритмов решателя воспроизводится в GUI как js-код: распаковка
геометрии, развёртка массивов, вычисление производных величин.

Такие модули размещаются в services/solver/ и подчиняются правилам:

- модуль содержит только вычисление: он не читает файлы, не обращается к схеме, не знает о
  Tabulator и не хранит состояние;
- каждая перенесённая функция снабжается ссылкой на источник: файл и имя функции julia,
  версия или дата снимка;
- перенос выполняется по исходному коду решателя, а не по комментариям, документации или
  образцам файлов;
- расхождение js-реализации с julia-оригиналом считается дефектом GUI независимо от того,
  какая из реализаций «удобнее».

Схемы вкладок вызывают эти функции в дескрипторах вычисляемых свойств и в кодеках
вариантов отображения; 
собственных копий формул не содержат.

## Инструменты обработки значения
Каждое значение обслуживается тремя независимыми инструментами. Это основной
рабочий интерфейс разработчика: расширение редактора выполняется через них.

| Инструмент | Назначение                    | Реестр             | Точка входа         |
|------------|-------------------------------|--------------------|---------------------|
| formatter  | отображение значения в ячейке | formatterRegistry  | universalFormatter  |
| editor     | ввод значения                 | editorRegistry     | universalEditor     |
| validator  | проверка ограничений значения | реестр ограничений | constraintValidator |

Общие свойства всех трёх:

- выбираются по `property.type` — тип данных определяет инструмент;
- получают дескриптор одним каналом: `formatterParams.property`,
  `editorParams.property`, явный аргумент `property`; при отсутствии —
  `resolveProperty(cell, schema)`;
- не анализируют схему, не ищут описание поля и не выбирают другой инструмент;
- не знают о типе хранения вкладки и о структуре таблицы.

Инструменты независимы: тип может иметь formatter без editor (нередактируемое
отображение) или несколько валидаторов при одном форматтере. Отсутствие
инструмента — штатная ситуация: `universalFormatter` возвращает пустое значение,
`constraintValidator` — истину; `universalEditor` сообщает об отсутствии
редактора явно.

Тип данных и ограничение — разные сущности. Тип определяет набор инструментов;
ограничение проверяется валидатором и применимо к разным типам.

Для `FIELD_TYPES.STRING` редактор перед завершением редактирования удаляет
начальные и конечные пробельные символы методом `trim()`. Все ограничения
строки, включая `minLength`, `maxLength`, `pattern`, `enum` и `const`,
проверяются уже для нормализованного значения. Нормализация относится к
пользовательскому редактированию: загруженное значение не изменяется
автоматически, пока поле не было отредактировано.

`property.enum` является ограничением допустимых значений скалярного свойства.
`FIELD_TYPES.ENUM` выбирает списочные formatter и editor, но не вводит
отдельного источника вариантов: они всегда берутся из `property.enum`.

### Именованные перечисления

`property.enum` задаётся непустым массивом вариантов
`{ value, label }`:

- `value` — типизированное значение StorageModel/BaseModel: строка,
  конечное число либо boolean; `null`,
  `undefined`, объекты и массивы не допускаются;
- `label` — непустая пользовательская подпись;
- значения вариантов уникальны и сравниваются строго, поэтому `1` и `"1"`
  являются разными значениями;
- для ограничения `enum` у базового скалярного типа тип каждого `value`
  соответствует типу свойства;
- `property.default`, если задан, обязан совпадать с одним из `value`.

`enumEditor` связывает DOM-option с индексом варианта и возвращает исходный
`value`, не строковое значение элемента `select`. `enumFormatter`
отображает `label`; если значение не найдено в перечне, показывает само
значение, чтобы несогласованность оставалась видимой.
`valueEnumValidator` проверяет значение по `entry.value`.

Для `FIELD_TYPES.ENUM` перечень обязателен. При создании значения по
умолчанию без явного `property.default` используется `value` первого
варианта. Рабочие схемы по общему правилу явно объявляют предметный default.

### Четвёртый инструмент: представление
Составное значение (ARRAY, OBJECT) получает View, выбираемое по
`property.view` через `ViewRegistry`. По умолчанию View размещается в
`DetailRegion` после активации ячейки-summary. Если схема объявляет
`views.main`, тот же ViewAdapter размещает выбранное свойство непосредственно
в основной области вкладки.

Связь инструментов для составного значения в DetailRegion:

- formatter возвращает в ячейку сводку значения и передаёт построение
  представления адаптеру;
- editor и validator ячейки-сводки не применяются: редактирование и проверка
  выполняются внутри представления, где действуют инструменты дескриптора
  элемента (`property.items`).

В основной проекции родительская ячейка-summary отсутствует; View работает с
тем же BaseModel-значением через явный binding адаптера. Размещение не меняет
`variantCodec`, `computedView`, ограничения элементов или сериализацию.

`arrayFormatter` — частный случай formatter'а, реализующий связь ячейки-summary
с DetailRegion для ARRAY. Собственной архитектурной роли он не имеет и заменяем
без изменения контрактов.

Для ARRAY с `variantCodec` адаптер получает BaseModel-запись через контекст
вкладки, codec выбирает представление по значениям объявленных зависимостей,
а `TableView` строит полученные строки и колонки. Статические атрибуты ARRAY
являются безопасным fallback. Вариант не создаёт новый View и не требует
отдельной регистрации в `ViewRegistry`.

`rowsMutable: false` означает, что строки имеют предметные имена и
фиксированный состав. Их значения редактируются, но добавление, удаление и
перемещение запрещены как в панели, так и в общем обработчике операций.

### Добавление типа данных
1. константа в `FIELD_TYPES`;
2. formatter и регистрация в `formatterRegistry`;
3. editor и регистрация в `editorRegistry` — если тип редактируется;
4. валидаторы ограничений и регистрация по типу — если тип имеет ограничения;
5. поддержка сериализации, если представление в файле нетривиально;
6. описание атрибутов дескриптора в документации `schemaFactory`;
7. для составного типа — адаптер представления и регистрация в `ViewRegistry`.

Диспетчеры при этом не изменяются.

## Согласование набора ключей StorageModel
Набор ключей StorageModel определяется схемой вкладки.

- При чтении файла ключи, не объявленные в `schema.properties`, в BaseModel не
  переносятся и при последующей записи не сохраняются.
- Свойства схемы, отсутствующие в файле, получают значение `property.default`.
- При записи файла формируется актуальный набор ключей редактора.
  Обычные свойства и `computeStored` входят в StorageModel; `compute` не
  читается, не объявляется ожидаемым ключом и не сериализуется. Одноимённый
  входной ключ `compute` считается неизвестным и диагностируется WARNING.
  Загруженное значение `computeStored` не является источником истины:
  после чтения оно заменяется результатом пересчёта.

Чтение и запись выполняют приведение файла к актуальному набору данных
редактора. Расхождение состава ключей файла и схемы не блокирует загрузку и не
является ошибкой, но диагностируется уровнем WARNING: неизвестные ключи
отбрасываются, отсутствующие свойства получают значение по умолчанию.

Следствие для схемы: все ключи, требуемые расчётным модулем, должны быть
объявлены в `schema.properties`, при необходимости через `property.storageKey`.

## Конфигурация вкладки
Вкладка описывается схемой, создаваемой `createSchema`. Схема объявляет:
идентификацию (`id`, `title`), источник данных (`directory`, `file`, `storage`),
оформление и дескрипторы свойств (`properties`).

Для видимого свойства основной таблицы RECORDS необязательный
`property.columnWidth` задаёт положительную целую ширину колонки в пикселях.
`TableBuilder` применяет этот атрибут одинаково для всех RECORDS-схем; выбор
ширины по имени свойства или идентификатору вкладки запрещён. Ширина служебной
колонки RECORDS и раскладка CLUSTER остаются отдельными контрактами.

### Нормативный каркас схемы

Рабочая схема явно объявляет `id`, `title`, `file`, `storage`,
`required` и `properties`. Общие идентификаторы вкладок и файлов берутся
из `TABS` и `FILES`. `directory` не указывается для штатного каталога
`input3XX`, поскольку это значение `createSchema` по умолчанию.

Минимальный каркас CLUSTER:

```js
import {
    FIELD_TYPES,
    FILES,
    STORAGE_TYPES,
    TABS,
} from "./common/constants";
import { createSchema } from "../schemaFactory";

export default createSchema({
    id: TABS.GENERAL.id,
    title: TABS.GENERAL.label,
    file: FILES.GENERAL,
    storage: STORAGE_TYPES.CLUSTER,
    required: true,

    properties: {
        parameter: {
            type: FIELD_TYPES.FLOAT,
            label: "Параметр",
            description: "Назначение и единицы измерения",
            default: 0,
            digits: 6,
        },
    },
});
```

Минимальный каркас RECORDS:

```js
import {
    FIELD_TYPES,
    FILES,
    STORAGE_TYPES,
    TABS,
    VIEW_TYPES,
} from "./common/constants";
import { createSchema } from "../schemaFactory";

export default createSchema({
    id: TABS.ELEMENTS.id,
    title: TABS.ELEMENTS.label,
    file: FILES.KVS,
    storage: STORAGE_TYPES.RECORDS,
    required: true,

    properties: {
        name: {
            type: FIELD_TYPES.STRING,
            label: "Название",
            description: "Название записи",
            default: "",
        },

        values: {
            type: FIELD_TYPES.ARRAY,
            view: VIEW_TYPES.TABLE,
            label: "Значения",
            description: "Табличное значение",
            default: [],
            nColumns: 2,
            order: "column",
            columns: ["Колонка 1", "Колонка 2"],
            items: {
                type: FIELD_TYPES.FLOAT,
                description: "Элемент табличного значения",
                default: 0,
                digits: 6,
            },
        },
    },
});
```

Примеры задают форму действующего контракта, а не готовые предметные схемы:
идентификаторы, ключи, подписи, defaults и ограничения заменяются сведениями
конкретной вкладки.

### Правила дескрипторов и оформления

- Видимое свойство явно объявляет `type`, `label` и `default`.
  `description` задаётся, когда он добавляет назначение, единицы измерения
  или условие применения; пустой текст не заменяет содержательное описание.
- Предметный default объявляется явно и не выводится из formatter/editor.
  Для ARRAY с `nColumns` default задаётся плоским значением StorageModel и
  при загрузке преобразуется `arrayShape`.
- `storageKey` указывается только при несовпадении имени свойства BaseModel
  с ключом или точечным путём StorageModel.
- ARRAY с табличным представлением объявляет `view`, `items` и `default`.
  Матричная форма дополнительно объявляет `nColumns`, `columns` той же
  длины и при необходимости `order`; без `order` действует `"column"`.
- `itemLabels`, `itemLabelTitle` и `itemLabelWidth` относятся только к
  подписям строк ARRAY-представления и не входят в BaseModel.
- `rowsMutable: false` задаётся для фиксированного состава строк. Отсутствие
  атрибута означает, что структурные операции разрешены. При создании новой
  записи матричный ARRAY с фиксированными строками получает полную BaseModel-
  форму из плоского `property.default` через `arrayShape`.
- `variantCodec` применяется только к ARRAY, объявляет непустой список имён
  свойств `dependencies`, функции `decode` и `encode` и необязательную
  `onDependencyChange`. Имена зависимостей относятся к той же BaseModel-записи.
- `computedView` применяется только к ARRAY с табличным представлением и
  объявляет внешние вкладки `dependencies`, чистую функцию `rows` и readonly-
  колонки `columns`. Он расширяет только ViewModel и не изменяет ARRAY.
- `views.main: { property }` объявляет основную View-проекцию единственного
  ARRAY-свойства RECORDS-схемы. Проекция не меняет BaseModel, StorageModel,
  сериализацию и правила optional-файла.
- Явная функция `summary({ rowData, value, presentation })` нужна только для
  предметной сводки. `presentation` является результатом `decodeArrayView`;
  сводка вариантного ARRAY использует его строки и не повторяет правила codec.
  Без функции адаптер показывает стандартный текст с числом строк. Summary
  является представлением и не содержит вычислительную логику модели.
- В основной таблице `RECORDS` назначение свойства (`property.description`)
  показывается в tooltip заголовка колонки. Tooltip ячейки показывает полное
  отформатированное значение только при его обрезке шириной ячейки или лимитом
  summary. Для `CLUSTER`, где свойства расположены строками, описание остаётся
  tooltip ячейки значения.
- `columnHeaderWordLines: true` применяется только к основной таблице
  `RECORDS`: каждое слово `property.label` отображается на отдельной строке
  заголовка без изменения самого `label`. Высоту строки заголовков Tabulator
  подбирает автоматически по самой высокой колонке.
- `stretchLastColumn: true` сохраняет подбор ширины колонок по содержимому и
  передаёт свободную ширину основной таблицы её последней видимой колонке.
  По умолчанию свободная ширина остаётся фоном строки. Параметр не изменяет
  раскладку связанного `TableView`.
- Атрибут `property.readonly` является действующим запретом редактирования
  свойства. `compute` и `computeStored` всегда readonly по своей семантике.
  Неиспользуемые верхнеуровневый `readonly` и `rowsInitiallyCollapsed`
  исключены из контракта `createSchema`; `views.main` является действующим
  контрактом размещения основного ARRAY-представления.
- Для FLOAT атрибут `floatFormat: "fixed"` задаёт десятичное представление без
  экспоненты; `digits` сохраняет число значащих цифр. Без этого атрибута
  действуют прежние режимы `floatExp` и `toPrecision`.
- Вычисляемое свойство объявляет ровно один объект `compute` или
  `computeStored` с непустым `dependencies` и функцией `evaluate`.
  `storageKey` допустим только для хранимого `computeStored`.
- Контракты вариантного представления и вычисляемых свойств являются
  действующими.

Действующие значения оформления:

| Элемент | Значение по умолчанию | Изменение схемой |
|---|---:|---|
| подпись свойства CLUSTER | 250 px | `rowLabelWidth` |
| номер записи RECORDS | 70 px | нет |
| основная ARRAY-проекция | выключена | `views.main.property` |
| раскладка заголовка свойства RECORDS | обычная | `columnHeaderWordLines` |
| растяжение последней видимой колонки основной таблицы | выключено | `stretchLastColumn` |
| подпись строки ARRAY | 70 px | `itemLabelWidth` |
| минимальная ширина колонки ARRAY | 120 px | нет |
| максимальная высота связанной таблицы | 240 px | нет |
| максимальная длина summary | 80 символов | `summaryMaxLength` |

Значения по умолчанию сохраняются, если содержимое не требует иного.
Переопределение выполняется существующим атрибутом схемы; локальные копии
общих констант оформления не создаются.

Для ARRAY-свойства с матричной формой дескриптор объявляет `nColumns` и при
необходимости `order` со значением `"column"` или `"row"`. Значение по
умолчанию — `"column"`. Атрибут `storageKey` может быть простым ключом или
точечным путём по вложенным объектам StorageModel.

Перечень вкладок редактора задаётся `tabRegistry`. Прикладной валидатор вкладки
сопоставляется её идентификатору в `modelRegistry`. Добавление вкладки —
создание схемы, регистрация в `tabRegistry`, регистрация валидатора в
`modelRegistry`. Изменение диспетчеров при этом не требуется.

## Валидация
Проверка ограничений ячейки: `constraintValidator` выбирает набор проверок по
`property.type` из реестра ограничений. Дескриптор поступает явным аргументом
либо через `resolveProperty`.

Прикладная проверка модели: `modelValidator` обходит `tabRegistry`, для каждой
вкладки вызывает валидатор из `modelRegistry` и накапливает диагностику.

### Предметные ограничения исходных данных

Пользовательские ограничения — это требования пользователя к допустимым
значениям отдельных элементов исходных данных. Разработчик явно переносит их
в `property` или `property.items`; проверку выполняет `constraintValidator`.
Если нужен новый общий вид ограничения, разработчик реализует валидатор и
регистрирует его в реестре ограничений по `property.type`.

Ограничения, вытекающие из режима, связей между полями, математической или
физической модели, разработчик явно программирует в валидаторе соответствующей
вкладки, зарегистрированном в `modelRegistry`; их проверяет `modelValidator`.

Полный набор ограничений не выводится автоматически из типа поля, формата файла
или описания модели. Задание пользовательских ограничений и программирование
модельных ограничений в обоих случаях требуют прямого участия разработчика.
Для каждого ограничения фиксируются источник, условие применимости,
затрагиваемые поля, уровень диагностики и автоматические либо ручные проверки.

**MC-ELEMENTS-001.** При `general.fullAxialSymmetry === true` число
азимутальных образов элемента `elements.symAs` (ключ StorageModel `sym.as`)
должно быть чётным. Это условное межвкладочное правило относится к модельной
валидации, а не к безусловному ограничению целого значения.

Безусловное пользовательское ограничение `minimum: 1` действует для
`elements.symLs`, `elements.symAs`, `elements.symPs` и `regions.symLs`.
Как и остальные ограничения ячейки, оно помечает значение, но не блокирует
редактирование или сохранение промежуточного задания.

Запуск ручной — из панели задания; результат передаётся в `diagnosticService`,
статус пересчитывается при каждом запуске. Результат ручной проверки без
собственных замечаний формирует запись уровня SUCCESS, но объединённый список
показывает её только при полном отсутствии WARNING и ERROR как в диагностике
модели, так и в диагностике загрузки. Диагностика не сбрасывается при
изменении данных, но сбрасывается при смене задания.

Диагностическая запись без `tab.id`, включая общий SUCCESS, является
информационной и не служит целью навигации. Переход на вкладку разрешён только
для адресуемой записи с `tab.id`; UI и обработчик навигации оба сохраняют
эту границу.

## Диагностика загрузки
До публикации выбранного задания `Tasks` проверяет наличие обязательного
каталога `input3XX`. При его отсутствии данные всех вкладок выбранного
задания не загружаются, состояние прежнего задания очищается и показывается
модальное окно с объяснением причины. Начальный фокус устанавливается на
кнопке закрытия окна.

Канал доставки диагностики отдельных вкладок: необязательный
аргумент-коллектор `dataService.load(dirHandle, schema, diagnostics)`.
Отсутствие файла обязательной схемы (`schema.config.required === true`)
создаёт ERROR, отсутствие файла необязательной схемы — WARNING. Неудача одной
вкладки не блокирует загрузку остальных вкладок.

Диагностика загрузки замещается при каждой загрузке вкладки; ручная проверка
модели её не сбрасывает. Общий уровень определяется объединением обоих
наборов. Пустое объединение означает, что проверка модели не выполнялась:
выполненная проверка всегда оставляет хотя бы одну запись.

## Цепочка отображения
Отображение — работа одного из трёх инструментов (см. «Инструменты обработки
значения»):

Schema → TableBuilder → universalFormatter → formatterRegistry → formatter

Для скалярного значения formatter возвращает представление значения в ячейке.
Для составного значения formatter возвращает сводку и передаёт построение
представления адаптеру. Основная проекция передаёт тому же адаптеру явный
model-backed binding:

formatter → ViewRegistry → ViewAdapter → View (TableView) в DetailRegion → Tabulator
schema.views.main → ViewRegistry → ViewAdapter → View (TableView) в основной области →
Tabulator

Симметричные цепочки: ввод — universalEditor → editorRegistry → editor;
проверка — constraintValidator → реестр ограничений → валидаторы.

## Инварианты
- Описание свойства для ячеек получается только через `resolveProperty()`;
  прямой доступ к `schema.properties` допустим лишь там, где нет `cell`.
- Дескриптор элемента связанного представления доставляется одним каналом:
  `formatterParams.property` (отображение), `editorParams.property`
  (редактирование) и явный аргумент `property` функции `constraintValidator`
  (проверка ограничений).
- `table._gui.schema` заполняется для каждого создаваемого экземпляра Tabulator,
  включая ARRAY-представления в области деталей и в основной области.
- Вычисляемые колонки ARRAY-представления читают внешний снимок BaseModel
  только через binding адаптера, являются readonly и не входят в преобразование
  строк представления обратно в BaseModel.
- Межвкладочную ревизию наблюдает слой вкладки; он обновляет активный
  `TableView` независимо от размещения, без прямой подписки View на
  `modelService`.
- Экземпляр Tabulator не размещается внутри ячейки другого экземпляра Tabulator.
- Инвариантные опции экземпляра Tabulator объявляются один раз
  (`COMMON_TABLE_OPTIONS`) и распаковываются каждым создателем таблицы.
  Опции конкретного вида представления остаются собственностью создателя.
- Сортировка по заголовкам отключена во всех основных и связанных таблицах
  исходных данных. Это сохраняет порядок записей `RECORDS`, элементов `ARRAY`
  и свойств `CLUSTER`, заданный моделью или схемой. Если структурные изменения
  разрешены, порядок изменяется только явными операциями перемещения строк.
- Нарушение ограничения ячейки не блокирует ввод: значение фиксируется и
  сохраняется, ячейка помечается как непрошедшая проверку. Режим highlight
  действует во всех экземплярах Tabulator, включая таблицы связанных
  представлений.
- Активная пара «запись + свойство» определяется так: свойство задаётся
  активацией ячейки-сводки, запись — последней выделенной записью основной
  таблицы. Изменение выделения переносит представление на последнюю выделенную
  запись без смены свойства.
- Пока связанное представление `RECORDS` отображается, его исходная
  ячейка-сводка отмечается синей внутренней рамкой. Рамка не изменяет размер
  ячейки, не заменяет состояние валидации и переносится вместе с активной
  записью.
- Если запись — владелец связанного представления удалена из основной
  таблицы, активная пара прекращает действие, представление закрывается и
  рамка снимается. Снятие выделения без перехода к обычной ячейке само по себе
  не закрывает существующую пару, пока запись-владелец остаётся в таблице.
- Щелчок по обычной ячейке основной таблицы `RECORDS`, не являющейся
  ячейкой-сводкой ARRAY, прекращает действие активной пары: связанное
  представление закрывается, область деталей возвращается к подсказке, рамка
  снимается. Работа внутри области деталей и её панели не прекращает действие
  активной пары.
- Активная таблица назначается при активации вкладки и повторно перед обычной
  операцией списка. Реактивная ревизия выделения позволяет индивидуальной
  команде панели определять доступность без второй копии данных таблицы.
  Setter активной таблицы не создаёт реактивную зависимость у вызывающего
  эффекта: активация таблицы деталей должна сохраняться до выбора
  другой таблицы.
- Строки связанного представления имеют техническое поле идентичности,
  объявленное опцией `index`; отображаемая нумерация хранится отдельно.
- Для `rowsMutable: false` структурные операции отсутствуют в панели и
  блокируются общим обработчиком независимо от способа его вызова.
- Служебная подпись строки является презентацией: она не входит в BaseModel,
  не сериализуется и формируется единственным владельцем — модулем `rowLabel`.
  Правило подписи одинаково при построении строк и при пересчёте после
  структурных операций.
- Ячейка строки, содержащей `arrayIndex`, хранит отдельный элемент значения,
  а не массив: связанное представление к ней не применяется.
- Каталог задания передаётся в `dataService` явно; глобальное состояние выбора
  сервисом данных не читается.
- Внешнее изменение BaseModel применяется слоем вкладки последовательно;
  устаревшая ревизия отбрасывается, если уже известна более новая.
  Transient source ID и признак применения не входят в BaseModel и не
  сериализуются; собственная публикация редактора не возвращается в ту же
  таблицу.
- При замене объектов строк активная область деталей закрывается: её View
  был связан с прежним объектом Tabulator ViewModel.
- Общий пересчёт завершается до публикации revision. Собственные результаты,
  представленные одной строкой, применяются точечными transient-патчами той же
  revision; структурное изменение числа строк и внешний update применяют
  полную BaseModel.
- Вычисляемое свойство недоступно для редактирования независимо от типа:
  BOOLEAN не переключается щелчком, а ARRAY не допускает изменения значений
  и состава строк.

## Панель вторичной функциональности и история

`SidePanel` является общей выдвижной панелью приложения. Режим видимости
вычисляемых колонок хранится только в реактивном `viewSettingsService` и
имеет три значения: «По схеме», «Показать», «Скрыть». Режим общий для вкладок,
но применяется редактором к своей активной таблице; он не входит в BaseModel,
StorageModel и Undo/Redo. Вычисляемые колонки выделяются приглушённым цветом
шрифта и остаются readonly.

На вкладке элементов панель дополнительно показывает команду выбора локальной
характеристики. Команда недоступна без загруженного задания или выделенных
элементов. Панели структурных операций RECORDS-вкладок также полностью
недоступны до загрузки задания; они не создают временную несохраняемую модель.

Ниже визуального разделителя панель показывает историю текущей вкладки.
Истории независимы по `schema.id`; редактирование одной вкладки не объединяется
с несвязанными изменениями другой. Undo и Redo публикуют обычную внешнюю
ревизию BaseModel через `modelService`, поэтому редактор применяет результат
тем же каналом, что и другие внешние изменения. Транзакции объединяют несколько
публикаций одной операции, новая правка очищает redo-ветвь, а смена задания
очищает всю историю. Максимальная глубина истории одной вкладки — 100 действий.

## Область деталей (DetailRegion)
Область деталей — часть вкладки редактора, расположенная под основной таблицей.
Отображает связанное представление активной пары «запись + свойство».

Ответственность:

- размещение представления, полученного через `ViewRegistry`;
- отображение подсказки при отсутствии выбора;
- предоставление панели операций над строками представления.

Область деталей не строит представление и не знает типов данных: она получает
представление от адаптера. Разметка представления не уничтожается при
освобождении области — она перемещается; жизненным циклом представления владеет
ViewAdapter.

Одновременно отображается одно связанное представление.

## Автоматические контрактные проверки
Чистые функции модельного и solver-слоёв проверяются встроенным тестовым
раннером Node.js. Команда `npm test` запускает файлы `test/*.test.js`
без браузера, Tabulator и запуска приложения.

Тесты импортируют рабочие модули непосредственно и не содержат копий
проверяемых алгоритмов. Контрактный набор охватывает форму ARRAY,
сериализацию, вычисляемые свойства, вариантные изменения, локальную историю,
производные величины элементов, раскладку MHJ, операции локальной библиотеки,
групповое назначение характеристик, модель графиков и чистую проверку
возможностей File System Access API. Фактическое открытие системных диалогов,
разрешения браузера, Chart.js и отображение модальных сообщений проверяются
вручную.

## Точки расширения
- Новая вкладка: схема + `tabRegistry` + `modelRegistry`.
- Новый тип данных: см. «Добавление типа данных».
- Новый вид представления: адаптер + регистрация в `viewRegistry`.
- Новое ограничение отдельного значения: атрибут дескриптора; для нового
  вида ограничения — валидатор и регистрация в реестре ограничений по типу.
- Новое модельное ограничение: реализация в валидаторе соответствующей
  вкладки и регистрация в `modelRegistry`.
